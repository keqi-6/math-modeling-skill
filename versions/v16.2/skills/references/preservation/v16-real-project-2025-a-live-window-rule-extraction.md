## 3. 跨项目规则取舍

### 3.1 纳入现有 owner 的规则

1. **来源题先证实，再传播。** 探索性新技巧先留在来源组件；达到预定效果并通过相应
   E1/E2 后，才能声明为跨题兼容传播。正式对账仍一次完成，不增加逐题回填门。
2. **消费者按真实含义选择。** 代码、讲解稿、图和说明只有在其内容或引用确实受影响时
   才进入同一 ChangeSet；“相关文件看起来可能有关”不是全量刷新理由。
3. **每问内容隔离。** 每份 `solution_brief.md` 只完成本问十节责任；跨问复用在本问
   问题分析、模型建立的公式引用或模型检验的退化/一致性检验中就地说明，不增设元叙事章。
4. **一条正式主链。** 候选算法、解析锚点、剪枝、历史方案和代理指标按真实角色进入
   内部比较或主链步骤，不能在队友稿/论文中并列成互相竞争的多个正式模型。
5. **边界自然落位。** 条件、适用域和不能推出的结论紧邻相应假设、公式、结果或结论；
   不另堆“安全声明”，也不以减少声明为由隐去实质边界。
6. **表达同步不重开技术门。** S7 后不改变模型、结果、代码、方法角色或主张强度的文本
   与讲解稿修订是 G1；真实语义变化仍按最早层或 compatible-change 闭包处理。
7. **并行写面服从当轮授权。** 多窗口可共享只读设计，但写路径应互斥，并为权威状态指定
   一个 writer；发现同路径并发写或无法归属的状态变化时，只停止冲突步骤并重新划界。
8. **人工/外部上传目录不是默认工作面。** 用户明确声明由队友上传或只供参考的目录保持
   只读；canonical 技术主稿仍写项目 `docs/`，不因可生成 DOCX 就复制到该目录。

### 3.2 不进入通用 Skill 的项目事实

- 三枚烟幕、投放间隔、下沉速度、圆柱目标、FY1—FY3 和具体评价公式；
- Q3 当前 S7、Q4 当前阶段、具体共享源码路径和 state writer 是哪个窗口；
- 某次搜索预算、方案数、时长、优秀论文数值和本题结果；
- “以最新时间戳为权威”的一次 R2 修复决定；脱离那次用户授权，mtime 不能压过正式
  identity、题面、规格、结果或验证证据。

## 4. 与 V16 本轮修复的关系

该活动窗口独立重现了 2024 B 题审查得到的三条关键边界：一问一稿、跨问关系局部表达、
S7 表达更新不应触发整套技术门。它还补充了来源题先验证、并行写面、唯一状态 writer、
人类上传目录只读和“不堆安全声明”的实施细节。

因此本文件可支持现有 `MOD.RESULTS.TEAMMATE_BRIEF`、`GOV.AUTH.WRITE_SCOPE` 和
compatible-change 方法程序的解释，但不凭一份项目新增状态节点、第五技术轴、并发锁服务、
DOCX 工件门或新的持久回执。
