# 14 — 跨会话接管与状态恢复

## 职责与强度

本文件执行控制器所选恢复级别要求的复读、恢复、暂停记录和节点收尾同步，不根据摘要决定事实，也不
复制论文、算法或排版规则。全量复读、摘要非权威、证据恢复、状态真实性和收尾同步为
用户已确认的 A/B 规则；全量复读只在 `R2_FULL_RECOVERY`、里程碑或最终闭合触发，
`R0/R1` 按控制器规定使用检查点或哈希增量证据。检查点文件和脚本为 C/D 实现。

## 目的

在新窗口、上下文压缩、人员交接或长任务恢复时，保持阶段管道和证据链连续。交接文件
是导航与状态声明，不是事实权威，不能替代原题、方法、代码、输出和论文。

## 项目级交接文件

在项目根目录使用 `HANDOFF.md`，至少记录：

- 项目用途、适用规范和评审能够看到的材料边界；
- 原始题目、外部要求和师生沟通记录的准确路径；
- 当前阶段、已通过的阶段出口条件和最早未完成阶段；
- `题目 → 方法 → 代码 → 输出 → 验证 → 论文` 的当前状态；
- 关键模型、成立条件、验证状态和未解决风险；
- 最近完成、回退和明确禁止重复的操作；
- 当前论文页数、附录口径、编译状态和交付同步状态；
- 新会话强制阅读顺序及建议首条指令。

题目专用节点、数值、老师姓名和当前结论只能写入项目根目录的 `HANDOFF.md`，不得写入
本通用 skill。

## 新会话恢复流程

先由 `SKILL.md` 选择 `R0_INCREMENTAL_CHECKPOINT`、`R1_HASH_DELTA_RECOVERY` 或
`R2_FULL_RECOVERY`。新会话本身至少触发 R1，但不自动等于 R2；只有来源未知、基线
缺失或过期、显式全量审计、里程碑或最终闭合才执行下面的全量流程。R0/R1 仍须验证
检查点、活动变化和受影响消费者，不能只读摘要后续做。

### R2 全量恢复步骤

1. 先读取 `project_state.json` 与 `HANDOFF.md`，只把它们当成定位项目和暂停点的待验证
   导航，不据此宣布现状或直接续做；
2. 读取 `skills/SKILL.md` 和全部编号 skill，取得完整恢复与审计规则；
3. 重新枚举项目内全部文件，不能复用旧文件清单代替当前枚举；
4. 完整读取每份唯一文本、代码与配置，提取 Office、PDF、结构化或二进制材料并按载体
   检查；图片和评审可见 PDF 必须视觉检查，镜像与重复件以哈希和内容比较证明一致；
5. 覆盖核对原题、附件、模板、沟通记录、planning、参考文献、数据、方法文档、代码、
   冻结输出、验证、论文源、图表、PDF、附录、归档、日志、镜像和未知文件；
6. 建立“题目—决定—方法—代码—输出—验证—论文—交付”当前证据链，再逐项验证
   检查点和交接声明，不得只抽查方便读取的层；
7. 判断最早未完成、失效或被新问题重新打开的阶段，从该阶段继续管道；
8. 在任何项目写操作前，向用户复述全量恢复结果、冲突、风险和下一步。

文件很多不构成跳过理由。可用批量提取、索引和哈希去重降低重复读取成本，但“看过
目录名”“读过 HANDOFF”“抽查几个输出”均不等于完成恢复。缓存、锁文件和编译中间
文件也要被枚举和归类，只是不把它们当成独立事实来源。

如果 `HANDOFF.md`、README、planning、代码输出和论文相互冲突，不选择“看起来最新”
的一份继续。按证据优先级查明原因，退回最早失效阶段，并先修正交接文件。

## 持续检查点与自动恢复

不要等待会话结束才写交接。把 `project_state.json` 作为机器可读的实时检查点，并在
以下事件发生后立即更新：

- 用户批准、拒绝或复议一项决定；
- 完成一次实际修改、求解、验证、编译或审计；
- 当前阶段、最早失效阶段、待确认问题或下一动作发生变化；
- 工作即将进入耗时工具调用、上下文压缩或其他可能中断的边界。

实时检查点至少保存：当前阶段及状态、最后完成事项、精确暂停点、下一动作、待确认
事项、当前权威审计、受影响文件、验证/编译状态和更新时间。不得把聊天中的计划写成
已完成事项，也不得在检查尚未执行时把验证状态设为通过。

新会话按以下顺序自动确定恢复点：

1. 读取实时检查点中的“最后完成事项—精确暂停点—下一动作”；
2. 比较检查点、`HANDOFF.md`、当前审计和受影响文件的修改时间；
3. 用论文、输出和验证证据核验检查点声明；
4. 若人工交接落后但实时检查点能被证据重现，以实时检查点恢复并随后同步人工交接；
5. 若二者均无法重现，退回证据链中最早能够确认的完成点，不猜测断联前的意图。

项目可使用 `skills/scripts/session_checkpoint.py` 原子更新实时检查点。该脚本只记录
已发生的状态，不替代证据核验，也不自动批准模型、论文或交付决定。

### 主动收尾检查

用户结束当天工作或任务抵达自然暂停点时，不只留下聊天总结。按控制器选择的恢复/闭合
强度在同一轮完成；普通暂停执行变更路径及消费者复核，里程碑或最终闭合执行全量复核：

1. 变更完成后重新枚举受影响路径、消费者和同步镜像；只有 R2、里程碑或最终闭合才复读
   全项目。检查局部修改影响的术语、公式、数字、图表、
   引用、代码、输出、文档、状态、日志、归档和交付镜像；
2. 由实际文件重建同步状态，不能先相信旧检查点，也不能以已执行复制命令证明同步；
3. 将最后完成事项、精确暂停位置、下一动作和待复议事项写入机器检查点；
4. 使 `HANDOFF.md` 中的论文页数、编译状态、证据链和恢复入口与实际文件一致；
5. 把当日产生且可跨项目复用的方法写入对应 skill，只写判据与程序，不写题目专用
   节点、数值或结论；
6. 校验全部 skill 的交叉职责与结构，更新工作日志，并同步约定的交付镜像；
7. 对全部应同步文件作内容比较，并确认没有只修局部载体、遗漏其他依赖表达。

Skill 重组收尾还须检查所有稳定规则 ID。任何待人工确认删除项必须继续可见；若规则
迁移到新职责文件，原位置或迁移表必须能够定位新归属。在用户逐项批准前，不以“已经
有相似规则”为由删除原条目。

若当天只改了方法论或交接文件，不得为“收尾完整”而额外改论文或重新排版。若论文
没有变化，也无需重复编译；交接中沿用最近一次已验证的编译状态并注明其来源。
但仍须完成与本轮变更及消费者相称的只读复核，用文件内容确认“无需传播”，不能因本轮
授权范围较小而省略同步影响判断；若当前属于里程碑或最终闭合，仍执行全量复核。

## 管道连续性

交接不得把阶段管道改成“读取摘要后直接改论文”。恢复时使用以下规则：

- 纯表达问题从 COMMUNICATE 恢复，但仍核对相关公式、结果和术语；
- 数字或图表不一致从 BUILD 或 VERIFY 恢复；
- 约束、目标、假设或可执行性问题从 DESIGN 恢复，并使全部下游产物失效；
- 原题、附件或规则理解变化从 SOURCE 或 UNDERSTAND 恢复；
- 外部文献改变选模依据时从 EVIDENCE 恢复。

完成一个阶段或发生实质回退后，更新 `HANDOFF.md`、阶段状态和工作日志。不要只在聊天
中留下新状态。

## 评审可见性检查

交接时明确最终评审能看到什么。若评审只能看到论文：

- 论文必须自足解释关键模型、术语、结果、验证和边界；
- 不得用项目路径、文件清单、README、聊天记录或“详见代码”承担证明责任；
- 内部文档可支持复现和审计，但不能被论文当作读者已经掌握的前置知识。

## 安全规则

- 不在交接文件中记录密钥、个人账号或与任务无关的隐私信息；
- 不把历史计划伪装成当前结论；
- 不把未编译的源文件状态写成已交付 PDF；
- 不把局部检查写成全流水线通过；
- 不因交接摘要声称“已完成”而跳过必要验证。
