# 项目范围与可执行计划

适用于新项目定向、现有项目重规划、混合请求拆解和范围变更。完整读取本包后形成当前任务的最小完整计划；不要把它扩成全项目启动清单。

## 规范边界

本包是非规范性操作包，不新增 `MUST`、状态、路由或授权。正式效果与判定仍由以下 owner 唯一拥有：

- `rules/project.json` 中 `PRJ-SCOPE-001`、`PRJ-PLAN-001` 和命中的 `PRJ-STRUCTURE-001` atoms；
- `rules/governance.json` 中实际命中的 mode、authorization、route 和 owner atoms；
- `references/runtime-policy.json`、`references/semantic-plan.schema.json`、`references/route-contract.json`；
- 组件状态、恢复和工件分别由各自机器契约拥有，计划只能引用，不能重定义。

执行时的最小闭包是“当前请求与项目事实 + 命中的 atoms + 本包 + 当前步骤直接需要的机器契约”。不因做计划而加载全部领域方法、全部规则或全部项目文件。

## 先把完整请求翻成问题边界

先保留请求的整体结构，再按依赖拆步骤。不要用单个关键词、目录名、既有 `qN` 命名或常见竞赛模板推导任务。

对当前请求回答：

- 现实对象和当前项目身份是什么；哪些官方材料、既有决定和当前文件可作为事实；
- 用户要求回答、估计、预测、优化、解释、修改或交付什么；
- 哪些输入可用，哪些输入尚缺，哪些只是候选来源；
- 硬约束、软约束、资源、期限、运行环境和评审可见边界是什么；
- 预期产物由谁消费，什么观察能判定其完成；
- 哪些相邻工作明确不在本轮或项目范围内。

每个纳入任务保留一个请求子句、官方要求或已批准范围变更作为依据。为了“计划看起来完整”而新增的分析、模型、图件、报告、目录或自检不进入范围。

## 只升级会改变结果的歧义

把歧义分为两类：

- 会改变目标、约束、评价口径、数据解释、方法选择、允许主张或交付边界的歧义；
- 不改变这些内容、可在现有授权内采用可逆工作假设的操作细节。

对第一类列出候选解释、各自影响、可用证据和需要谁决定。优先查官方材料、用户既有明确决定和当前权威事实；仍存在真实取舍时，请用户一次性决定相关组。对第二类记录假设和回退条件即可，不因一个细节阻断无依赖步骤。

沉默、旧代码存在、AI 已写草稿或某方法常见都不是项目选择。已有明确决定在语义兼容时直接继承；新证据会实质改变决定时才重新打开。

## 建立三类稳定清单

范围盘点用三个并列清单即可，载体按项目现状选择，不强制创建文件：

1. 问题或独立任务：来自题面或请求的稳定身份、当前边界和目标输出；
2. 共享证据：会被多个问题消费的数据、解释、外部来源、规格或正式结果；
3. 交付物：最终消费者、格式来源、允许与排除内容、验收观察。

把每一项链接回包含项、排除项或交付边界。成功条件写成可观察结果，例如“指定输入下约束残差在已批准容差内并有独立复算”，而不是“模型合理”“效果较好”或“流程完整”。

## 按失效边界拆组件

适合独立成组件的对象通常满足至少一项：

- 有自己的正式输入、决定、状态或验收证据；
- 上游变化时会独立失效；
- 会被多个问题复用；
- 产生有稳定消费者的正式 identity。

章节、文件夹、脚本编号和通用阶段名不自动成为组件。同一共享数据或规格不要在各问题中复制 owner；相反，不要把所有问题压成一个项目级阶段字段。组件类型和状态集合取自当前契约，不在计划中另造一套。

## 用生产者—消费者关系代替线性待办

对每个工作包形成一张简短卡片：

| 字段 | 内容 |
|---|---|
| `work_package` | 一个可验收的技术动作，不是宽泛愿望 |
| `scope_anchor` | 请求子句、问题身份或已批准范围变化 |
| `dependencies` | 真正必须先成立的输入、决定或上游 identity |
| `owner` | 负责生产当前结果的组件；不是规范 owner 的替代品 |
| `evidence` | 完成后要观察或验证什么 |
| `deliverable/consumer` | 结果流向何处、由谁读取 |
| `failure_effect` | 失败只阻断哪些后继工作 |
| `next_action` | 可立即执行的动作及明确 blocker |

把边组织为无环的生产者—消费者图。可以并行的独立步骤并行；前一步失败只阻断依赖它的后继步骤。用户在一个自然语言请求中已经授权的连续步骤可以同轮完成，不在每一步后索要标准口令或回执。

综合追踪链保持为：

`范围依据 → 工作包 → 依赖/决定 → 预期证据 → 产物/主张 → 消费者/交付物`

它描述工作组织，不覆盖状态迁移、恢复等级、危险命令授权或工件提升门。

## 计划顺序

按以下顺序收敛，而不是先选算法或先建目录：

1. 核对完整请求、官方边界和现有项目入口；
2. 写包含项、排除项、交付边界和可观察成功条件；
3. 处置会改变结果的歧义，继承仍有效的已批准决定；
4. 建立问题、共享证据和交付物清单；
5. 依独立状态与失效边界拆组件；
6. 连接生产者、消费者、证据和交付关系；
7. 形成技术主线、并行支线和真实 blocker；
8. 为活动组件留下一个可执行下一动作；
9. 只把真实取舍、冻结决定变化或范围变化提交人工复核。

完整项目计划优先回答“题目怎样被证据化地做出来”：题意、数据、基线、候选与选择、规格、实现、独立验证、稳健性、整合、论文和交付。排期、分工和治理是保障层，不能淹没技术依赖。

## 比例性与例外

- G0 咨询或一次性规划可以直接在回复中给出范围和依赖，不创建状态或计划文件。
- 小任务可以只有一个组件和一张工作包卡；不为凑齐流程制造空步骤。
- 现有项目只重规划受请求或变化影响的闭包；未受影响的已确认决定和证据保持有效。
- 初始范围不是永久冻结。后期变化记录范围差量、授权依据、受影响组件和重基线后的三类清单。
- 官方模板、提交规则或用户指定工具链构成已核验约束时服从该约束；Skill 偏好不能覆盖它。
- 范围事实不足但独立步骤仍合法时，先完成可执行部分并把其余项标成 blocked，不把整个请求退回。

## 人工复核点

只在以下边界主动停下：

- 两种可信题意解释会实质改变答案；
- 新证据要求改变已冻结的目标、模型角色、参数依据或交付边界；
- 新增任务超出原请求或现有契约授权；
- 时间、资源、准确性、解释性之间存在负责人必须承担的真实取舍；
- 计划将改变现有项目布局、正式 identity 或状态迁移。

不要把内部 route、tier、工作包关闭或步骤完成变成人工逐步回执协议。

## 常见失败与修复

| 失败 | 修复 |
|---|---|
| 从旧目录或模型反推题意 | 回到完整请求和官方材料，重建范围依据 |
| 用“做好、合理、完整”作成功标准 | 改写为可观察对象、测量和允许主张 |
| 对每个小不确定性都停下询问 | 只升级会改变结果的歧义，其余记录可逆假设 |
| 计划只有线性待办和时间表 | 补生产者、消费者、证据、交付和失败传播边 |
| 组件按章节或目录机械拆分 | 按状态、identity、复用和失效边界重拆 |
| 为显得全面增加未授权分析 | 删除无法回到请求子句或适用契约的任务 |
| 一个子步骤失败就停止全部工作 | 仅阻断依赖后继，继续独立步骤 |
| 计划自建阶段门或恢复规则 | 删除重复控制面，改为引用当前 owner |
| 范围变化后沿用旧清单 | 记录差量和授权，重建受影响清单与依赖 |
| 下一步写成“继续研究/完善模型” | 写成组件、动作、输入和 blocker 都明确的可执行项 |
