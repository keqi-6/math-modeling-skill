# V9 Skill 维护契约

## 触发与禁止自动修改

只有用户明确要求修改、增加、合并、废弃、审计或发布本 Skill 时进入 `skill_maintenance`。普通建模任务中发现缺陷只能报告，不能自动改写 Skill。

## 变更分类与风险

| 等级 | 范围 | 最低验证 |
|---|---|---|
| L0 | 无语义格式、错别字 | 静态检查 |
| L1 | 澄清、示例、非规范文本 | 引用和相关回归 |
| L2 | 领域规则或路由行为 | 影响分析、正反例、路由与行为回归 |
| L3 | 状态、权限、Schema、恢复或维护协议 | 完整契约验证、差分测试、明确迁移记录 |
| L4 | 删除核心能力或改变维护内核 | 新主版本、全量回归、独立回滚点、新调用验收 |

## 强制流程

1. 把请求写成旧行为、新行为、触发、例外、作用域和风险等级。
2. 在能力注册表和所有 canonical owner 中搜索同义、相邻、相反规则。
3. 计算能力、路由、状态、Schema、模块、评测和版本影响。
4. 只修改 canonical owner；不得通过再复制一段强规则修复冲突。
5. 新能力必须有稳定 ID、触发条件、预期行为、禁止行为、owner、路由和测试。
6. 项目特例默认保留在项目配置，不升级为全局规则。
7. 对实质变化添加至少一个正例、一个近似反例和一个冲突或混合意图场景。
8. 运行 `scripts/validate_release.py`；L2 以上还要运行真实或隔离的前向场景。
9. 修改后的行为必须由重新加载新版 Skill 的新调用确认。
10. 报告能力变化、冲突裁决、修改文件、测试、兼容性和回滚点。

## 维护不变量

- 一个语义只有一个 canonical owner。
- 没有消费者的文件不创建。
- 没有测试的强制能力不发布。
- 不以固定措辞存在代替行为正确。
- 不用 catchall 证明路由可达。
- 不复用已发布能力 ID。
- 删除和冲突裁决必须保留去向，不静默消失。
- 当前编辑上下文不能自行证明新版 Skill 已被重新加载。

变更提案使用 `receipt.schema.json` 的 `skill_change` 分支，并由 `scripts/analyze_rule_change.py` 验证。
