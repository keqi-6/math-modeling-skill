## 接手已有项目

用户说"接着做/回顾一下"时：

`README.md`、`HANDOFF.md` 和 `project_state.json` 只用于定位材料和形成待验证的恢复
假设，不能作为项目现状的事实权威。R0/R1 核验检查点或哈希基线、实际变化和受影响

**致命反模式**：仅凭 README、状态文件、代码或部分输出推断完整项目逻辑并开始修改。

## 方法证据层级

遇到冲突时依次采用：当届竞赛官方文件；题目原文、原始数据与可复现实验；正式教材、标准和同行评议论文；有明确来源的讲座；AI 提示词、经验模板和往届答案。低层资料不能覆盖高层要求。官方未规定的篇数、字体、模型数和公式数只能标为建议。

## 项目目录约定

```
project/
├── src/<task-id>/       按真实任务边界组织的脚本
├── src/_utils/          共享工具
├── output/<task-id>/    按任务或稳定生产阶段分区的冻结产物
├── docs/<task-id>/      逐问解决方案讲解、推导、验证、复现和答辩材料，不承担论文草稿
├── planning/            规划文档
├── paper/               论文
└── README.md            进度 + 关键数字速查
```

`data/` 保存只读原始输入；`planning/` 保存理解、调研、方案决策、状态和论文落点映射，但不写连续论文正文；`references/` 保存 URL/DOI、书目、笔记和合法全文；`src/` 是计算逻辑来源；`output/` 是程序生成的冻结结果；`docs/` 面向逐问解决方案讲解、方法、推导、验证、复现和答辩，不承担论文草稿；`paper/` 是唯一论文工作区与最终评阅载体；`skills/` 只记录跨赛题方法，不写某题参数和答案。

### 逐问解决方案讲解稿

每一问完成 S6 时，建立并经人工审阅 `docs/<task-id>/solution_brief.md`，使负责该问的
成员能够把完整方案交给队友讲解。它采用论文“模型建立与求解”最通用的解释顺序，
但属于技术交接物而不是论文草稿。至少包括：

1. 本问要求、题意解释和边界；
2. 现实对象到变量、参数、关系、目标和约束的映射；
3. 关键假设、依据及其影响；
4. 模型建立，包括符号、公式或计算关系及各自作用；
5. 模型求解，包括输入、算法、参数以及停止、可行性或最优性判据；
6. 关键结果、单位及现实含义；
7. 独立验证、不确定性或稳健性证据、适用边界与禁止宣称；
8. 对应代码、冻结输出和复现路径；
9. 队友必须能够复述的最小结论，以及仍待决定的问题。

讲解稿可以复用已批准的数学式、结果、表格和图，但不得用摘要、论文节号、评阅者话术
或正式结论语气伪装成论文正文。S7 写论文时可以把它作为技术来源之一，按论文结构和
表达要求选择、重写并交叉核验；讲解稿通过不等于论文内容获批，也不得整篇自动晋升。

讲解稿的表达质量必须进入正式路由：完整读取 `13-excellent-paper-expression.md`，采用
其中对象先行、定义—动作—理由—证据—落点、术语绑定本题作用、条件先于结论和声明
强度等可迁移规则；完整读取 `17-reader-first-manuscript-audit.md`，采用术语首用、邻近
白话解释、普通读者复述和数据含义等门。两文件中只服务于正式论文的摘要职责、全文
章节齐备、节次、篇幅、排版和稿件晋升条款不适用于讲解稿，必须记录为已检查但因产物
身份不触发，不能因“不适用”而跳过相关文件的完整读取。

### 初始化后的目录职责落地

创建空目录只证明脚本执行过，不证明项目已经初始化完成。用户接受标准目录后，立即
把已确认的官方题面、附件和模板以非破坏性副本落入 `data/`，保留原来源位置，并用
哈希或逐字节比较证明一致；文件过大、目录关系复杂、存在命名冲突或复制会损害来源
语义时，改用明确的指针清单。临时锁、缓存和来源未定文件不得混入官方数据。

逐一检查其他目录：其初始权威文件已经存在，或明确标记由哪个后续阶段产生。不得以
“目录已经创建”代替职责落地检查，也不得在 `data/` 仍为空且无指针时宣布初始化闭环。

### 技术做题计划优先

`planning/project_plan.md` 的主体首先回答“这道题怎样做出来”，按真实技术依赖列出
题意拆解、原始数据审计、探索分析、简单基线、候选模型与选模理由、人工选模、数学
规格、逐问求解、独立检验、稳健性、跨问整合、论文和复现审计。阶段管理、时间排程、
协作治理和提交合规保留为附录或并列保障项，不能淹没技术主线。每一步写清产物和完成
判据；通用阶段名不能替代当前题目的具体动作。

多问项目还必须把该链条实例化到每一问及具有独立输出的每个小问或情景。每个任务显示
当前子阶段、关闭证据和下一道禁止越级条件；不得只写一段通用流程或给整问一个状态。
已有代码、图表或验证若越过未批准的方法决定或数学规格，只能登记为草稿或部分证据，
不能反向关闭上游阶段。详细子阶段职能与恢复审计见 `15-pipeline-methodology.md`。

## 代码规范（硬性要求）

### 注释风格
**使用中文注释，服务于维护、复核和答辩，而非写成语法教程。**优先说明代码块的职责、
输入输出及其对应的数学动作。对非显然实现、边界处理、参数选择和容易误改的设计，
简要说明理由、来源或所实现的方法条款；完整推导、替代方案比较和长篇参数论证放在
方法文档中，并由注释给出对应位置。不逐行解释通用语法，也不使用“显然”“经验设置”
等无证据说明。

### 产生结论的脚本必须有冻结输出
- 产生论文数字、图表或下游输入的脚本必须冻结输出，禁止仅 stdout
- JSON 适合指标和小型结构；NPZ、CSV 或 Parquet 适合矩阵和表格
- 产生结论、冻结产物或下游输入的程序必须提供中文可读的输入、输出和职责声明。声明
  可位于脚本头部中文注释、中文 docstring、集中式程序清单或工作流配置中，但必须能
  从脚本快速定位，并与真实读写行为一致
- 单文件脚本或没有集中工作流清单时，极其推荐使用以下头部格式：
  ```
  # 输入: xxx.xls / output/<task-id>/xxx.json
  # 输出: output/<task-id>/yyy.json
  # 职责: 用中文说明该脚本完成的数学或数据动作
  ```
- 输出声明必须与实际文件写入完整一致，不限于 `json.dump` 或 `np.savez`
- 禁止写"输出: stdout"但实际有 json 落盘

### 产物路径
- 生成产物按真实任务边界或稳定生产阶段分区，避免不同问题、情景、模型版本和实验
  批次在同一目录混杂。
- 多问项目默认可使用 `output/<题面任务ID>/`，但任务 ID 必须来自原题和任务矩阵，
  不得根据惯例创建 `q3` 等不存在的任务。单任务或其他项目可按数据阶段、模型、情景
  或运行版本组织。
- 在运行清单或产物登记中声明每个目录的职责、生产者和消费者。是否允许全局清单位于
  `output/` 根目录，由项目目录契约决定，不作绝对禁止。

## 文档规范（硬性要求）

### Markdown与LaTeX格式边界

项目中的 `README.md`、`HANDOFF.md`、`planning/**/*.md` 和 `docs/**/*.md` 只使用
Markdown语法。数学关系使用清楚的普通文字、行内代码、纯文本代码块、引用块或
Markdown表格表达，不嵌入MathJax/LaTeX定界符和命令。正式论文的LaTeX语法只写入
`paper/` 下的 `.tex` 源文件；若使用独立草稿目录，其入口、状态与正式论文的隔离按
`02-latex-setup.md` 执行。

该边界约束项目成果格式，不禁止本通用skill为了讲解论文构建而在代码围栏中展示必要的
LaTeX示例。审计时搜索项目Markdown中的LaTeX数学命令只能用于定位候选，命中代码路径、
历史审计说明或被引用的外部原文时需按上下文判断。

### 数字可追溯
每个进入论文、方法文档或重要决策的数字都必须按身份追溯：

- 题面或附件数据：定位原始文件、页码、工作表、单元格、记录或图示；
- 外部数据和规则：定位可靠来源、访问版本和引用位置；
- 假设、阈值和人工设置参数：定位依据、适用条件及用户确认记录；
- 程序派生结果：定位冻结产物、字段或表格位置、生产脚本和输入版本；
- 定义、单位换算和教学示例：明确标注身份及推导，不伪装成实测或求解结果。

支撑论文结论或下游计算的程序结果不得只存在于 stdout。冻结载体按数据结构选择，
不强制全部使用 JSON。

### 数值表述
精确计数和精确求解结果不得用“约”掩盖错误；测量值、估计值和舍入值可以使用“约”，但必须交代精度、区间或舍入规则。关键数字必须能追溯到冻结产物的字段或表格单元。

### 方法论文档规则
- 每节对应一个脚本或一组紧密关联的脚本
- 程序派生数字必须来自冻结产物；其他数字按上述身份回到各自证据源，不可凭记忆复制
- 复现命令必须列出所有脚本

### 导航文件一致性

README、HANDOFF、项目状态或其他导航文件如果展示当前数字、版本、页数、验证状态或
结论，必须与对应的真实证据源一致。程序派生数字核对冻结产物及生产链；其他数字按
身份核对。导航文件不承担结果权威：发现冲突时先沿原始输入、方法、代码、冻结产物、
论文和验证证据定位最早错误层，再更新导航文件，不得为了迁就 README 修改正确结果。
不承载这些信息的 README 无须额外增加数字速查。

## AI 使用合规

先在项目 README 声明用途和适用规范，不同用途不得混用：

- **正式 CUMCM 参赛**：根据《人工智能工具使用规定（2025 年试行）》，使用 AI 生成的内容须在正文相应位置标注，所用工具须列入参考文献，支撑材料须包含 `AI 工具使用详情.pdf`。该 PDF 至少记录工具名称和版本、使用目的和环节、关键提示词与回复、采纳内容及人工修改情况。未使用 AI 时，应在参考文献之后按官方规定声明。每届提交前仍须检查官网是否发布替代版本。
- **Nature Portfolio 解释框架**：不能取消竞赛的明文提交义务，但可解释竞赛未定义的
  AI 使用边界。人类原文的语言润色属于辅助编辑；模型讨论、代码、分析或正文生成属于
  实质性辅助；大语言模型不列为作者，人类必须复核并对最终内容负责。Nature 场景通常
  集中披露，竞赛场景的标注位置仍服从当届明文。

## 人工主导：先深交互，再确立产出

题意、模型、参数、验证、结论和论文产出必须在与用户深交互后确立。AI先说明：
- 为什么这样写？
- 理由来自哪里（赛题原文/数据事实/文献/数学推导）？
- 存在哪些可信替代方案、各自会改变什么？
- 当前内容是AI建议、待审草稿，还是用户已经确认的项目权威？

用户确认后，AI可以分担已确定范围内的资料整理、代码实现、运行、复算、排版和一致性
检查；若新证据会改变题意解释、评价标准、模型、参数依据、结论或交付范围，必须暂停
机械推进并重新交互。不得把用户未反对、旧代码已存在或AI先生成了草稿视为用户同意。

新项目的空目录和模板同样是一种流程产出。先与用户确认项目用途、适用规范、目录结构
和协作边界，再运行 `scripts/bootstrap_project.py`。为支持讨论而形成的候选提纲或
内部草稿必须明确标记“待审”，不得进入当前权威文件、冻结结果、正式论文、正式提交
包或正式交付镜像。明确用于团队审阅且不冒充正式成果的协作镜像可以包含草稿，但须
保留草稿标记，并在导航和交付清单中与正式交付物分开。
