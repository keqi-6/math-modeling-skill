# 项目方法提示（非规范性）

本文件只提供实施选项，不创建任何规范义务。权限入口、路由/状态/工件机器契约与策略 atom 的唯一 owner 见 `ownership-contract.json`。

## minimal-platform

初始化前先辨认已有入口、数据目录、源码、稿件和构建方式。V10 的默认控制面只有 `.modeling/state.json`；后续目录随已准入工件的父路径按需出现。一个常见但非默认的成熟项目可能最终包含源码、数据、结果、稿件和图表目录，也可能继续沿用用户原有布局。

准备工件提案时可以直接读取 `artifact-contract.json` 的当前 `required` 与属性定义；本方法提示不镜像字段清单、枚举或禁用路径，以免形成第二个会漂移的规范源。

## scope-and-decomposition

可按以下问题检查范围：

| 维度 | 典型问题 |
|---|---|
| 输入 | 哪些数据或题面事实确实可用？ |
| 未知 | 要估计、预测、优化或解释什么？ |
| 约束 | 硬约束、软约束、资源和时间边界是什么？ |
| 指标 | 怎样判定一个方案优于另一个？ |
| 产物 | 谁会读取哪项结果？最终格式由谁规定？ |
| 排除项 | 哪些看似相关的扩展不在本次任务中？ |

组件拆分以独立状态和失效边界为尺度：需要单独证据、会被不同输入失效、或能被多个问题复用的内容，通常适合作为独立组件。只为排版方便而拆出的章节不必成为状态组件。

范围盘点可以用三个并列清单表达：问题身份、可被多个问题消费的共享证据、最终交付物；清单项再链接到包含项、排除项或交付边界。后期范围变化的记录示例可包含范围差量、授权依据、受影响组件和重基线后的清单，初始范围不必因此被误解为永久冻结。

综合计划的一条说明性追踪链可以是 `work_package -> dependency -> evidence -> deliverable`。它表达工作包从何处取得输入、如何验收以及交付到哪里，不替代状态机的阶段或恢复契约的失效规则。

## recovery

恢复时先辨认三类事实：权威状态、已登记工件身份、工作区差异。R1 的阅读集合来自“变化所有者 + 传递消费者”，不是固定文件清单。R2 重建可依次恢复题意边界、输入身份、冻结决定、运行身份、验证证据、稿件主张和交付边界。

用于解释恢复记录的示例矩阵如下；它不新增分级条件或完成门：

| 级别 | 说明性阅读窗口 | 说明性完成证据 |
|---|---|---|
| R0 | 权威状态与下一动作声明的直接输入 | 一致性结果与下一合法动作 |
| R1 | 变化所有者、受影响闭包及其声明输入 | 闭包成员的定向复核记录 |
| R2 | 重建完整证据链所需的权威输入与实际工件 | 可重算的覆盖清单及零缺口结果 |
