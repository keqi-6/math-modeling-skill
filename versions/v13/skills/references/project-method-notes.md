# 项目方法提示（非规范性）

本文件只提供实施选项，不创建任何规范义务。权限入口、路由/状态/工件机器契约与策略 atom 的唯一 owner 见 `ownership-contract.json`。

## minimal-platform

项目平台的规范 owner 是 `project-platform-contract.json`。初始化先辨认已有入口、数据目录、源码、稿件和构建方式，再把工作绑定到其中定义的逻辑角色；“按需创建”只决定目录何时物理出现，不允许自行发明角色或路径。

新项目从第一项真实工件开始采用规范路径，只创建该工件所需的父目录，不预铺空目录、占位文件或默认 README。既有项目先审计、后兼容：不自动移动或改名已有文件；新增文件仍进入规范角色路径。若确需继续向非规范路径新增文件，应把它作为单独的平台迁移请求交由用户批准。

G0/G1 工作不要求先创建控制文件；只有项目需要跨轮次保存正式状态、决定、受保护 identity 或 checkpoint 证据时，才按需建立 `.modeling/state.json`。

准备工件提案时可以直接读取 `artifact-contract.json` 的当前 `required` 与属性定义；本方法提示不镜像字段清单、枚举或禁用路径，以免形成第二个会漂移的规范源。

## scope-and-decomposition

可按以下问题检查范围：

| 维度 | 典型问题 |
|---|---|
| 输入 | 哪些数据或题面事实确实可用？ |
| 未知 | 要估计、预测、优化或解释什么？ |
| 约束 | 硬约束、软约束、资源和时间边界是什么？ |
| 指标 | 怎样判定一个方案优于另一个？ |
| 产物 | 谁会读取哪项结果？最终格式由谁规定？ |
| 排除项 | 哪些看似相关的扩展不在本次任务中？ |

组件拆分以独立状态和失效边界为尺度：需要单独证据、会被不同输入失效、或能被多个问题复用的内容，通常适合作为独立组件。只为排版方便而拆出的章节不必成为状态组件。

范围盘点可以用三个并列清单表达：问题身份、可被多个问题消费的共享证据、最终交付物；清单项再链接到包含项、排除项或交付边界。后期范围变化的记录示例可包含范围差量、授权依据、受影响组件和重基线后的清单，初始范围不必因此被误解为永久冻结。

综合计划的一条说明性追踪链可以是 `work_package -> dependency -> evidence -> deliverable`。它表达工作包从何处取得输入、如何验收以及交付到哪里，不替代状态机的阶段或恢复契约的失效规则。

## recovery

恢复时先辨认三类事实：权威状态、已登记的受保护工件 identity、与当前动作有关的差异。working 文件变化只定位精确引用旧 identity 的证据；milestone、frozen、final identity 变化时，R1 阅读集合才扩展到变化所有者和声明的下游消费者。R2 仅在状态缺失/损坏且当前动作依赖它、关键变化无法归属，或用户明确要求全量恢复时重建相应证据链。G3 只审计声明的交付范围；只有该审计实际发现上述 R2 条件时才进入 R2。

用于解释恢复记录的示例矩阵如下；它不新增分级条件或完成门：

| 级别 | 说明性阅读窗口 | 说明性完成证据 |
|---|---|---|
| R0 | 权威状态与下一动作声明的直接输入 | 一致性结果与下一合法动作 |
| R1 | 变化所有者、受影响闭包及其声明输入 | 闭包成员的定向复核记录 |
| R2 | 重建完整证据链所需的权威输入与实际工件 | 可重算的覆盖清单及零缺口结果 |
