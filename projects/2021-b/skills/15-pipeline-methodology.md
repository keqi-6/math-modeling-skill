# 15 — 数学建模全流程认知地图

## 职责与强度

本文件维护阶段、依赖、回退、逐问闭环和变更传播，不制定详细成果写法，也不把阶段
状态当质量评分。题意来源、证据链、最早失效层、依赖传播和人工边界为 A/B；阶段名称、
记录文件和表格结构为 C/D。当前无删除候选；十阶段不能机械要求同名文档或固定顺序。

## 目的

让 agent 知道完整完成一道数学建模题通常需要做什么、各项工作为什么存在、何时需要
回看前面的判断。它不是自动做题机、评分器或强制排程系统；阶段可以交叠、合并和回退，
具体深度由题目、时间和用户判断决定。

整张地图服从“人工确立、AI分担”：AI负责降低阅读、搜索、计算、编程、复核、绘图和
整理的压力；用户在充分了解证据、替代方案、后果和不确定性后，决定题意、指标、假设、
模型、参数、验证、主张和交付。任何待审草稿都不能因被AI写入文件而自动成为项目权威。

## 方法论来源与取舍

方法论的来源类型不决定规则强度。讲座和优秀论文中经独立验证的数学正确性、真实性、
证据链和同步要求可以成为 A/B 级规则；固定句式、固定数量和体裁偏好通常只能作为
C/D 级条件或建议；机械错误、过度绝对或未核验来源进入 E 级待人工处置。执行阶段按
规则强度和适用条件调用，不能把整个来源文件统一视为“建议”或“硬规范”。

本管道综合以下公开范式：

- `handsomeZR-netizen/mathmodel-skill`：吸收定向启动、题目选择、逐子问局部回修、
  环境预检和提交合规意识；不吸收评分状态机、自动 verdict、固定图表数、固定变量数
  或默认扰动幅度。
- `usail-hkust/LLM-MM-Agent`：吸收“问题分析—结构化建模—计算求解—报告生成”的
  核心分解和按问题检索模型知识；补入其端到端概述中较弱的独立验证、语义审计、声明
  边界和变更失效。
- `xiaomacoltai/math-modeling-skill`：吸收建模、编程、论文三角色之间的回退条件和
  复现清单；不采用固定交付格式或每问模型数量限制。
- 公开优秀论文与本项目完整实践：保留概念限定、数据能力边界、公式—代码—结果—
  论文双向追踪、逐页视觉检查和适用范围审计。

GitHub 仓库是工作流启发来源，不是竞赛规则或数学正确性的权威。正式要求仍以当届官方
文件为准，模型正确性仍以题目、数据、推导和独立验证为准。

## 十类必要工作

| 工作层 | 核心问题 | 完成迹象 |
|---|---|---|
| 0 ORIENT | 做哪道题、在什么规则和资源下完成 | 赛制、题目、期限、交付物、团队与环境已知 |
| 1 SOURCE | 原始材料究竟包含什么 | 全部输入有处置、哈希和阅读状态 |
| 2 UNDERSTAND | 题目每个名词和量词究竟要求什么 | 概念审计、任务卡、依赖图通过 |
| 3 DATA | 数据能支持哪些结论 | 模式、质量、单位、代理边界和基线冻结 |
| 4 EVIDENCE_DESIGN | 为什么选这个模型、如何证明它够用 | 候选比较、规格、基线、验证和声明计划获准 |
| 5 SOLVE | 每个子问是否形成可复核答案 | 逐问纵向闭环通过 |
| 6 INTEGRATE | 各子问是否仍描述同一个系统 | 继承、版本、符号、假设和跨问验证一致 |
| 7 STRESS | 结论在哪些条件下成立或失效 | 风险匹配的稳健性、局限和适用范围 |
| 8 COMMUNICATE | 评审只看论文能否理解和核查 | 声明双向映射、正文与 PDF 完整 |
| 9 AUDIT_SUBMIT | 当前交付是否可复现、合规且无陈旧产物 | 全链重跑、视觉审计、镜像与提交包通过 |

这些工作不是必须机械串行。数据异常可能迫使重新解释题意，求解结果可能暴露选模错误，
论文质疑也可能揭示概念边界缺失。关键是识别“最早出错层”，从那里修正，而不是只改
最后的文字。

## 逐子问纵向闭环

全局统一设计之后，不要先写完所有代码再统一验证。按任务依赖拓扑顺序逐问执行：

1. **规格**：固定输入版本、输出、变量、目标、约束、假设、基线、接受标准和允许声明。
2. **手检**：用最小样例、量纲、边界值或简单基线检查公式方向和数据接口。
3. **实现**：代码只实现已批准规格；所有结论冻结为结构化产物。
4. **求解**：保存参数、随机种子、运行环境、状态、候选域、界和停止依据。
5. **独立验证**：不用同一求解摘要复算关键约束和指标；按问题选择枚举、界、等价算法、
   守恒、反事实、交叉验证或回测。
6. **解释**：说明结果形成机制、相对基线的收益、代价、失败情形和给下游的输入。
7. **冻结**：记录输入哈希、代码版本、输出哈希和消费者。
8. **评审**：用户或审计确认后，任务才可作为下游权威输入。

只修复受影响任务及其传递依赖。不得因一个独立子问失败而默认重做全部，也不得因其他
子问通过而平均掩盖失败任务。

### 避免横向齐步造成认知过载

“逐问闭环”不仅约束代码顺序，也约束与用户讨论和决策的顺序。多问题项目完成共享题意、
数据和术语底座后，若各问方法不同、存在前后依赖或用户难以同时维护多套思路，应只打开
当前一问：

`本问题意与数据事实 → 本问文献导向 → 本问证据重审 → 本问基线 → 本问候选模型
→ 人工决定 → 本问实现与验证 → 本问解释与冻结`

不得因为全局流程进入“基线”“选模”或“稳健性”阶段，就一次要求用户决定所有问题的
不同方法。未轮到的问题保持关闭，其模型、参数、目标权衡和实验设计政策延后。此前形成
但未批准的跨问题方案应标记为被取代并归档，不让旧待决项继续出现在当前决策队列。

只有以下内容适合跨问共享：官方输入、已批准概念和术语、不会改变问题含义的数据接口、
通用代码、已经冻结且兼容的上游结论。共享不等于同步思考；后一问只在开始时继承真正
需要的部分。

### 保持各问的必要独立性

仅按顺序逐问执行仍不够；后一问不能默认继承前一问的思维形状。提出当前问的基线、
模型、验证或图件前，执行：

1. 只重述当前问的对象、动作、量词、输出和评价依据；
2. 不引用上一问模型，独立识别当前统计或决策单位、数据拓扑、缺测、重复结构和主要
   失败风险；
3. 从这些事实零起点生成候选，包括可信的“不新增模型”；
4. 逐项审计继承：
   - 共享事实和兼容接口可以复用；
   - 只有题目依赖链明确需要时才继承上游结论；
   - 方法部件必须由当前问重新证明用途；
   - 没有新职责的公式、稳健性检查、图形和正文顺序应拒绝；
5. 执行反事实检查：若隐藏上一问、旧代码和旧草稿，是否仍会选择并同样解释当前方法；
6. 建立直接回答映射：
   `当前问要求 → 方法动作 → 输出证据 → 验证 → 允许声明`；
   没有对应行的部件是思维惯性候选，不是创新；
7. 稳健性必须尊重当前问的真实单位和依赖。需要时保持区组、匹配、守恒、图结构、
   时间顺序或情景边界，不机械复用逐点删除、统一百分比扰动或上一问拟合指标。

在当前问分析或方法权威中保存简短继承台账：

| 项目 | 继承、重证或拒绝 | 当前问理由 | 后果 |
|---|---|---|---|

必要独立性不否认跨问依赖，而是否认用依赖代替选模。跨问一致性要求共享事实、单位和
已批准上游结论一致，不要求模型族、公式数量、验证形式、图件或论文结构一致。

若后期发现某个方法或压力测试主要因为“上一问也这样做”而存在，应回到最早受影响的
候选或规格阶段。仍成立的数据和计算保留为部分证据，但在当前问重新闭合前，不得继续
充当完整答案。

### 逐问路由表

每个活动问题按下表路由，不能只因某个专责模块存在就假定已经执行：

| 顺序 | 当前问题 | 责任模块 | 最小关闭证据 |
|---|---|---|---|
| 1 | 题意、对象、量词和输出 | `SKILL` Stage 2、`03` | 本问任务卡及人工确认 |
| 2 | 数据接口与手查事实 | `16` | 唯一输入接口、能力边界和核验事实 |
| 3 | 背景、领域机理、变量角色和方法谱系 | `08`、`12` | 文献导向稿及同步的 `references/` 记录 |
| 4 | 基线、候选方法和规格 | `07`、`09`、Stage 4 | 比较理由、验证计划及人工决定 |
| 5 | 实现、求解、独立验证和冻结 | `10`、Stage 5 | 可复算代码、冻结结果和验证 |
| 6 | 解释、适用边界和论文映射 | `03`、`05` | 声明边界、文献落点和用户复审 |

若第3步被触发而未关闭，不得把第4步候选升级为正式方法。检索中新发现的机理、变量角色、
方法前提或边界若改变既有理解，应回到最早受影响步骤，而不是把文献只装饰在论文背景。

### 把逐问流程实例化为可执行清单

路由表不能只停留在skill正文或项目计划中的一段箭头。对原题中的每一问，以及具有独立
输出或约束的每个小问、情景，必须在 `planning/project_plan.md` 实例化下列子阶段职能：

| 子阶段职能 | 关闭证据 | 未关闭时禁止 |
|---|---|---|
| 本问题意 | 原题任务卡和必要人工确认 | 不得提出正式模型 |
| 本问数据接口 | 字段、统计单位、候选域、缺测和能力边界 | 不得用未经批准的接口求结论 |
| 本问文献导向 | 触发判断；触发时有来源记录和导向稿 | 不得先选模后装饰性补文献 |
| 本问证据重审 | 数据与文献共同形成的事实、冲突和禁止声明 | 不得把探索图升级为正式结论 |
| 简单基线 | 可手算参照、结果和局限 | 不得只展示复杂候选 |
| 候选与充分性比较 | 包含“无需新增模型”的候选比较和验证计划 | 不得把AI建议当成人工决定 |
| 人工方法决定 | 用户理解替代方案后作出的明确记录 | 不得编写正式求解代码 |
| 数学规格 | 变量、关系、参数、约束、输出、接受标准和禁止外推 | 不得边实现边改变问题 |
| 实现与求解 | 与规格一致的代码、运行信息和结构化结果 | 不得从聊天或控制台抄结论 |
| 独立验证 | 不复用主实现的关键复算 | 不得声称技术完成 |
| 稳健性与解释 | 与声明风险匹配的失效检查、含义和限制 | 不得升级为论文正式结论 |
| 人工复审、冻结与论文映射 | 理解确认、冻结清单和声明落点 | 不得打开依赖本问的下一问 |

项目可使用S1—S12或其他稳定ID，名称也可按题型调整；但不得省略职能、当前状态、关闭
证据和禁止越级条件。若两个职能在简单问题中同轮完成，仍分别记录通过证据，而不是删除
阶段。若原题一问包含多个独立情景，必须分别核对输出和验证，不能用整问一个“完成”
掩盖遗漏。

每次恢复、回退或准备进入下一问时执行子阶段审计：

1. 从原题确认实际问题和小问集合；
2. 对每个任务标记当前最早未关闭子阶段；
3. 检查现有代码、输出或验证是否越过未关闭的人工决定或数学规格；
4. 越级产物只标记为草稿或部分证据，不能反向证明上游完成；
5. 将回退后的失效范围传播到实现、验证、解释、正文和下游问题；
6. 当前轮只执行最早未关闭子阶段允许的动作。

“总项目处于第几步”“当前处理第几问”和“本问处于哪个子阶段”是三个不同层次，必须
同时可定位。只有前两层而没有第三层，视为逐问流程尚未落地。

## 双完成门与可理解性

阶段或子问的“完成”至少区分两个层次：

1. 技术层：输入、方法、实现、冻结结果和独立验证可复现；
2. 人工理解层：负责人理解问题、基本算法、结果含义、替代方案和禁止外推，并作出需要
   的决定。

当团队声明相关基础薄弱时，方法文档同时保留技术复现层和通俗读者层。通俗层按
“问题—最小例子—本题计算—结果—现实含义—限制”组织。术语、公式、脚本成功、检查
通过或用户没有反对，都不能单独关闭人工理解门。若技术层已完成而理解层未完成，应暂停
依赖该理解的新模型选择，在计划和日志中明确记录，而不是撤销已经通过的计算证据。

### 理解复审的文本化接口

重要理解门不能只靠聊天解释。把通俗复审写入当前问题的分析或方法文档，并与技术层
直接相邻或互相链接。采用以下最小结构：

1. **题目要回答什么**：按现实对象拆开问题，不先罗列模型名称；
2. **最小数字例子**：用最小表格或两三项数字演示比较动作和容易误解之处；
3. **本题数据怎样对应**：说明统计单位、配对关系、缺测、重复和比较基准；
4. **每种方法只负责什么**：用一句普通话说明输入、动作和输出，避免术语清单；
5. **能够与不能够说明什么**：分开事实描述、模型概括、统计识别和因果声明；
6. **可信替代方案与信息增量**：包括“不新增模型”，说明复杂度、篇幅和结论变化；
7. **确认的准确含义**：列出本门确认了什么，以及尚未批准的模型、参数、代码和正文。

这个结构是信息职能清单，不要求机械使用七个同名标题。简单问题可以合并，复杂问题
可以展开，但隐藏术语和公式后，负责人仍应能够复述比较对象、方法作用、结论边界和
下一步决定。

人工理解关闭必须同时具备：

- 文本化通俗层已经落盘，不能只引用聊天记录；
- 用户明确确认理解，而不是仅说“继续”“可以”或没有提出异议；
- `planning/interaction_log.md` 区分理解确认与方法决定；
- 项目计划写明下一阶段仍禁止哪些尚未批准的动作。

理解确认不等于模型批准、参数批准、实现授权、正文批准或最终冻结。后续证据若改变
方法角色或声明边界，应重新打开受影响的理解门。

### 术语最小化与必要术语解释门

术语审计不只检查“有没有定义”，还要先检查“有没有必要出现”。对聊天、待审方案、
规划文档、分析报告、图表标题和论文依次执行：

1. **必要性检查**：只有术语会影响当前选择、保证方法可复现、避免概念失真或方便核验
   原始文献时才保留。只用于显示专业性、暂时不会参与判断的名称、历史别名和软件实现
   名称移到技术注或暂不引入。
2. **普通话先行**：先说明“在比较什么、怎样比较、结果说明什么”，再在确有用处时用
   括号给出一次规范名称。不得以术语定义另一个未解释术语。
3. **单轮术语预算**：一次面向人工决定的讲解只引入完成该决定所需的最少新概念。若
   连续出现三个新名称、缩写或外文词，应拆分讲解并删除非必要项。
4. **就地小例子**：保留的抽象术语首次出现时，用一个最小数字例子或本题字段说明其
   操作；只给词典式定义不算通过。
5. **去术语复述**：发起人工确认前，隐藏术语、缩写和公式，剩余说明仍须让负责人说清
   方案做什么、为什么使用、会怎样改变结论以及不能说明什么。

该规则不要求从代码、公式说明、文献索引和技术复现层删除规范名称，而是把“决定层”
与“检索复现层”分开：前者以理解为准，后者保留必要的标准称谓。

## 三种轻量记录

### 任务矩阵

复杂、多问或跨会话项目可在 `planning/task_matrix.md` 每个子问一行：

`任务 → 题面动作与量词 → 输入 → 输出 → 上游 → 模型状态 → 验证状态 → 论文落点`

它帮助检查“有没有漏问”和跨问依赖，不保存大段方法正文。简单项目可以直接把同样
信息写入 `planning/understanding.md`，不为满足格式额外建表。

任务矩阵中的题号必须从原题逐字提取，并区分“竞赛年份与赛题编号”和“题内问题与
小问编号”。原题是任务集合的唯一权威源；任务矩阵和论文目录只是派生核对源，不能因
文件名、历史代码目录、通用论文模板或惯常的“下一问”顺序自行增生任务。每次宣布进入
下一问、创建 `qN` 路径或新增带题号标题前，执行一次三处一致性检查：

`原题中的题号与任务 → 当前任务矩阵 → 当前论文标题结构`

若后两者与原题不一致，先修复派生产物；若原题尚未读清，不得猜测下一问。尤其禁止把
“某届竞赛的第三题”误读为“题目内部的问题三”，也不得把其他项目或旧版本遗留的
`q3` 等路径当作当前任务存在的证据。

### 声明台账

当论文声明多、证明边界容易混淆时，可在 `planning/claim_ledger.md` 每个重要结论一行：

`声明 → 对象/条件/范围 → 数据与模型 → 冻结结果 → 独立验证 → 论文位置 → 禁止外推`

它帮助约束摘要、结论、图表和模型评价。简单项目可把声明映射并入终稿审计，不强制
维护独立文件。没有验证状态或适用条件的重要声明不得升级为摘要 A 级信息。

### 变更影响记录

发生实质变化时，至少用工作日志、交接文件或项目状态中的一种方式记录：

`变更对象 → 原因 → 直接消费者 → 传递消费者 → 所需动作 → 关闭证据`

典型传播：

- 题意或量词变化：使理解、设计、相关任务、验证、图表和论文失效；
- 数据清洗或单位变化：使所有读取该字段的模型及下游失效；
- 假设、约束或目标变化：使相关任务求解及其声明失效；
- 仅文字改写：只重开 COMMUNICATE，但仍核对声明没有改变；
- 版式变化：重编译并重开受影响页面的视觉审计。

不要求实现自动依赖传播。agent 应根据真实生产链判断受影响内容，并向用户说明为什么
需要或不需要重算。失效不是删除历史；旧运行和审计可以保留追溯，但不能继续作为
“当前通过”证据。

## 已批准决定的继承审计

人工主导不等于让用户在每个子问中重复确认相同事项。进入相关子问或修改模型前，先对
已有人工批准决定做兼容性继承审计：

1. 找出可复用的概念定义、数据口径、候选域、假设、指标、优先级、责任政策和声明边界，
   并记录其批准来源；
2. 比较新旧任务的评价对象、决策对象、时间状态、约束前提、模型角色和证明目的；
3. 只有上述语义和作用均兼容时才直接继承，不因名称相同就机械复制整条目标链；
4. 将不兼容项分为“应删除”“应局部迁移”“存在真实价值冲突”三类，只把会改变 modeled
   reality、价值顺序、数学规格或声明范围的差异提交用户；
5. 向用户成组呈现继承项、差异项、理由和后果，不把一组能够统一判断的细节拆成连续
   的逐项确认；
6. 若任务内部模型角色不同，分别继承。例如覆盖潜力诊断可以继承覆盖与响应指标，但
   不应自动继承需要正式服务分配才有含义的工作量目标；
7. 继承后仍要检查公式、程序、冻结结果和论文是否真正实现，既有批准不能替代实现验证。

沉默不能批准新的实质选择；反过来，已经明确批准且经兼容性审计可直接复用的决定，也
不应被AI重新包装成未决问题反复询问。只有发现证据冲突、语义变化或可信替代方案会
实质改变结果时，才重新打开人工决策。

## 项目状态的边界

`project_state.json` 只用于长项目导航，可以非常简短。它不负责决定模型、自动批准
阶段、给子问打分或替用户作关键选择。若状态文件与题目、代码、冻结结果或论文冲突，
以证据为准并修正状态。

时间不足时可以降低候选比较广度和非关键展示，不能跳过题面核对、数据基本审计、关键
约束复算、结果冻结、主要声明边界和提交合规。agent 应把取舍与残余风险讲清楚，由
用户决定是否接受。

## 与论文结构的映射

执行顺序不等于论文目录。通常映射为：

- SOURCE、UNDERSTAND、DATA → 问题重述、问题分析、数据说明；
- EVIDENCE_DESIGN → 假设、符号、选模依据和模型建立；
- 每个 SOLVE 纵向闭环 → 对应小问的建立、求解、结论和检验；
- INTEGRATE、STRESS → 模型评价、稳健性、适用范围和推广；
- 声明台账 → 摘要、图表解读、结论和引用的双向追踪。

论文只呈现理解和核验所需内容，不复制状态机、文件路径或内部管理记录。
