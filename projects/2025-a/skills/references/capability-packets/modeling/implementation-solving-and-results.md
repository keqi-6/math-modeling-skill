# 模型实现、求解、冻结结果与解释

适用于按冻结规格实现代码、运行求解、生成正式结果和解释当前子问。执行项目代码仍受当前路由和 runtime action 授权控制；本包不因提供命令示例而授予执行权限。

来源保留：V8 `15-pipeline-methodology.md`、`25-model-results-acceptance.md`、`31-modeling-minimum.md`，结合 V14 的 ChangeSet、正式 identity、E1/E2 可触达性和结果主张边界。

## 实现分层

将实现分为：

`输入解析 → 规格实例化 → 候选/状态生成 → 求解 → 结果校验 → 正式输出登记`

代码只实现当前冻结规格，不边写代码边改变题意、目标或约束。接口、公式、参数、容差和输出单位保持同义；确需改规格时返回规格阶段。

每个影响结论的脚本说明输入、输出和数学职责。可手检小实例、固定种子例、边界输入和已知不可行例应能独立触达正式入口及关键分支。

## 求解逻辑必须可回放

论文和技术说明至少回答：

1. 初始候选、状态或搜索范围从哪里来；
2. 每一步新增、删除、固定或比较什么；
3. 按什么指标接受、排序或排除；
4. 怎样处理不可行和数值失败；
5. 用什么界、单调性、等价关系或停止条件结束；
6. 结束后能证明可行、局部不可改进、近似保证还是全局最优；
7. 数学输出怎样还原为题目要求的方案、条件、路线或判断。

软件名、求解器状态、间隙为零和变量规模只能作为补充证据，不能替代算法逻辑与证明边界。

## 数学合同与本次求解执行的边界

除本包后述的队友讲解稿固定十节格式外，一般论文和技术说明中的“模型建立”与“模型求解”描述内容责任，不强制使用同名标题。评审可见的方法链中，模型建立首次完整承载对象、变量、假设、关系、目标、约束、从原始关系到可计算形式的必要变形，以及决定正式模型身份和主算法合法性的求解逻辑。读者在这里应已理解为什么问题可求、按什么数学判据判断候选。

模型求解承接该合同，只说明本次实例怎样执行：实际输入和搜索域、初始化或候选生成、采用的参数与精度、执行顺序、停止和失败处置、以及输出怎样登记。它可以回指公式、给出操作性伪代码和实例化参数，但不得首次引入或完整重复一套决定目标含义、等价性或可行域的新数学合同。若实现时发现必须新增这种内容，应返回规格阶段，而不是在求解说明中补丁式建模。

近似边界按数学职能判断。为把连续条件变成可判定对象而必需的括区间、等价变形或接受规则属于模型合同；某次运行实际采用的网格数、种子和迭代预算通常属于求解执行。若离散网格本身就是模型定义，或某个容差改变了允许主张，它仍须在规格中冻结。闭式代入或直接推导可以没有独立“求解”章节，但不能因此省略公式到答案的可复推链。

## 确定性与随机执行

确定性运行保存输入 identity、代码版本、参数、环境、状态、输出和日志。随机运行另外保存种子策略、重复次数、失败运行、结果分布和稳定范围；不能只挑最好一次。

启发式或近似算法保留小规模精确对照、可行性修复、约束残差和可获得的上下界。无法证明全局最优时，结果措辞严格限制为实际证据支持的层级。

## 正式输出

终端中短暂出现的数字不是可检查结果。正式输出应有可打开载体、schema、单位、identity、运行 ID 和输入绑定。失败运行、容差、停止原因和候选域也应可追溯。

每个子问形成：

`规格 → 手检 → 实现 → 求解 → 独立验证 → 解释 → 冻结 → 人工复审`

相关子问按依赖拓扑推进；一个独立子问失败不默认重做全部，其他子问通过也不能平均掩盖失败。

## 结果解释的三层

1. **计算事实**：数值、方案、排名、约束状态和与基线的差异。
2. **模型内含义**：哪些关系、约束或权衡造成结果。
3. **现实外推**：在何种证据和条件下能映射到现实。

每上升一层都需要额外证据。结果段可按“基准—变化—形成原因—代价或例外—决策含义”组织；只列最大值、验证计数或程序输出不能替代回答。

区分固定原方案代入新参数与参数变化后重新优化：前者只说明既有方案指标变化，后者才说明最优决策是否切换。离散候选域最优不能写成连续域或现实全局最优。

## 直接回答与边界

每问末尾用普通语言给出题目要求的关系、方案或判断，并紧邻说明候选域、条件、限制和禁止外推。不要只写“结果见上文”。

最小 trace 为：

`result_id → question_id → frozen_spec_id → baseline comparison → verification refs → material limitations → consumers`

## 逐问队友讲解稿

### 产品身份与固定位置

每个实质问题都写一份可独立阅读的主稿，canonical 路径只能是：

```text
docs/<task-id>/solution_brief.md
```

例如第一问是 `docs/q1/solution_brief.md`。一问一份，不把多问合并进共享交接文档，也不用 implementation note、verification note、论文片段或聊天摘要代替。主稿的产品身份是 `technical_documentation`：面向队友理解、复述、答辩和后续写作取材，但不是正式论文正文、状态权威、运行手册或结果的第二数据源。

每份主稿只完成本问的职责，不设“贯穿全文定位”“统一全文主线”之类元叙事章节，也不把其他问题的模型、结果和后续计划混成大杂烩。真实的跨问继承应在本问需要它的位置自然出现：可在问题分析中说明承接关系，在模型建立中引用前问公式，在模型检验中给出退化或一致性检验。引用只解释本问为什么这样建模，不把后问的方向探针、候选或结果提前写成本问结论。

工程复现确有消费者时，可在同一 `docs/<task-id>/` 下按需增设 `implementation_note.md` 或 `verification_note.md`。这些 sidecar 保存命令、代码入口、输入输出、运行身份、hash、隔离方式和完整验证合同；不是每问强制齐套，也不能吞掉主稿必须解释的数学逻辑。正式论文另写入 `paper/`，只通过当前主张—证据—论文落点映射选择性迁移和改写已批准内容，不能整篇复制或自动晋升 `solution_brief.md`。

### 何时写与何时验收

讲解稿不在 S1–S4 持续回填，也不阻塞候选比较、规格或实现。最早可在 S5 已有可解释的当前实现与结果后用一个 G1 ChangeSet 起草；通常在 S6 独立验证期间，随着可用的 E1–E4、敏感性和边界证据一次成稿。草稿不需要额外 proposal、artifact registration、receipt、状态迁移或逐节门禁；尚未闭合的内容由计划/状态记录，不把 `provisional`、TODO 或内部状态头留在最终主稿中。

实际执行该问 S6→S7 关闭前，固定路径主稿必须已经完整、与当时的规格、结果和验证结论一致，并由真实人类阅读当时文件。人审至少让读者用自己的话复述：研究对象与问题、主模型机制、求解和判据、关键证据、直接结论、适用与禁止外推边界。文件存在、十节标题齐全、机器结构审计通过、提前给未来工作授权、技术 E1–E4 通过、自然暂停或“做收尾”都不等于这次接受。关闭证据记录被审文件 identity、当前规格/结果/验证绑定和实际决定；这是一条 S6 人类理解门，不是 E1–E4 之外的第五条技术轴。

S7 后的错字、措辞、段落组织、统一标题或不改变含义的公式排版属于 G1 表达同步，不重开 S6，不刷新模型 identity，也不要求再次补回执。若数学合同、冻结结果、方法角色、结论强度或主张边界真实变化，则先按变化本身的最早层 reopen 或 compatible-change 规则处理，并只更新真实受影响的讲解稿闭包；需要再次声明队友已接受时，绑定新文件 identity。不得因为一处兼容实现回传而机械重审所有问题，也不得借“纯表达”掩盖语义变化。

### 固定十节职责链

主稿第一行使用：

```text
# 问题X：……模型的建立与求解
```

随后按顺序使用十个二级章节；三级、四级小节可随模型复杂度自由展开，各问不要求等长、等式等量或图表等量：

1. `## 1 问题重述`：用题目语言说明本问要决定、计算或判断什么，写清对象、条件和范围；不提前堆结果。
2. `## 2 问题分析`：解释结构难点、容易犯的错误简化、选取当前路线的原因和总体责任链。
3. `## 3 模型假设`：列出成立条件、依据及其对结果的影响；假设不能冒充已观测事实。
4. `## 4 主要符号说明`：用表格索引跨节主要符号、含义和单位；它只是导航，不能替代公式附近的局部解释。
5. `## 5 模型建立`：完整给出对象、变量、关系、目标、约束、状态、可行域、必要变形和决定主方法合法性的数学合同。
6. `## 6 模型求解`：说明本次实例如何生成/枚举候选、初始化、排序或剪枝，采用何参数与精度，怎样处置不可行/数值失败，何时停止，最终能声称可行、局部、近似还是全局最优。
7. `## 7 模型结果`：按“条件或基线→值→形成机制→代价或差距→决策含义”报告结果；紧邻给出单位、方案 identity、并列关系和主张边界。
8. `## 8 模型检验与敏感性分析`：分开写内部手检、独立复算、结构检验、敏感性/稳健性与现实有效性或局限；“程序成功运行”不能充当通用验证。
9. `## 9 模型评价`：写真实的结构优势、计算代价和现实局限，不用空泛优缺点套话。
10. `## 10 问题X结论`：直接回答本问，重述最重要结果及成立边界，不引入新方法或新数值。

前四节可以紧凑，但必须自含；第五至第八节是技术主体，不能被压缩成模型名、公式清单、流程图或九项检查表。第十节的 `X` 与标题中的问题编号一致。

### 公式、表格、结果与图的写法

Markdown 主稿中的主要公式使用 `text` fenced block，并按首次出现顺序连续编号 `（1）`、`（2）`……。每组公式附近必须用正文说明：式中对象与随机性/条件、每个新符号和取值范围、单位、关系或函数的作用、它支撑哪一步求解或结论、不能据此推出什么。符号表不能替代这些就近说明；禁止让队友为了理解一个式子跨多节反查。

符号、主结果、情景比较和敏感性适合用 Markdown 表格。每个定量结果都绑定当前冻结输出和验证证据，写明计算条件、单位或量纲、方案/情景 identity、形成机制与结论强度。用于排序、并列和门槛判断时以冻结精确值为准，小数只承担展示。不能从终端抄数、手工改图或让讲解稿反向成为代码输入。

图只从冻结结果或验证结果脚本化生成，并保留输入与输出 manifest；只有主稿实际引用后才算它的消费者。图已生成不等于已进入主稿，更不等于进入论文。图后正文仍须解释它回答什么、读到什么、有什么边界。

讲解只展开正式主模型和主求解链。需要独立强数学合同的辅助验证器，把完整推导、命令和诊断留在验证证据/sidecar；主稿报告检验对象、设置、指标、结果及结论边界。若辅助方法实际决定正式结果或承担核心证明，就不能借“验证器”隐藏，应升格并回到模型选择与规格阶段。

正文只保留一条可解释的正式求解链。解析锚点、剪枝、候选生成器、历史方案、代理指标和不同优化器按真实角色嵌入该链或留在候选比较证据中，不并列叙述为多个互相竞争的“主算法”。这里约束的是最终角色，不禁止在模型选择阶段真实比较候选。

### 主稿中禁止出现的替代物

不要以状态、`spec_id`、`result_id`、run ID、hash、命令、代码路径、TODO、下一动作、回执、门禁清单或“队友必须复述的九项”开篇。这些信息各归状态、manifest、实现/验证 sidecar 和计划文件；主稿只保留理解本问数学与结论所必需的内容。成立条件、适用域与禁止外推应就近写在相应假设、公式、结果或结论处，不另堆“安全声明”清单；自然表达不等于可以删除实质边界。也不要照抄参考 DOCX/PDF 中未经当前证据批准的数学、数据或结论；参考稿最多提供表达节奏，不能取得权威身份。用户明确声明为队友上传区、人工交换区或只读参考区的目录不是 Agent 工作面；不在那里生成 Word 或讲解稿副本，除非用户另行明确授权该精确写入。

### 结构检查与人工读者检查

结构检查可确认 canonical 路径、唯一主标题、十节顺序、非空技术主体、连续公式编号和明显工作流元数据缺失；它只能证明载体合规。人工读者继续逐式、逐表和逐结论核对当前规格/结果/验证，并尝试不看原稿复述对象—机制—证据—结论—边界。若只能复述模型名、几个指标或运行步骤，回到最早缺失的内容责任修正。人审接受也只接受这份讲解稿及其边界，不自动批准正式论文、图表排版或最终交付。

## 变更传播

正式输入、规格、代码语义或结果 identity 变化时，只失效真实绑定旧 identity 的验证、图表、论文和下游子问。重新运行不是默认许可；先确认变化原因、受影响闭包和用户请求是否包含执行。
